# Server-owned preparation with visible trade-offs

The remote developer window previously offered local hardcoded outfit IDs and locked
preparation on its first connection. Starting health, movement and resolve-recovery
trade-offs were hidden until entry. It now inspects the authority's actual loaded
fitting catalog, compares those values together, combines an outfit with the existing
approach/technique, and commits explicitly. The table, technique description and lock
message were inspected in the actual source window; confirmed play names the accepted
outfit. Source/PCK OS input exercises the same flow.

The optional v1 catalog request is exact-key, bounded and read-only, once per unstarted
connection. It cannot assign resources, admit an action or begin the model. A second
request is rejected; a catalog request after entry cannot reopen preparation. Existing
headless hello clients retain compatibility. The interactive client accepts bounded,
typed, unique catalog items and technique IDs, then rejects a substituted confirmation
instead of silently accepting changed choices or resources. The server still revalidates
hello against its own loaded catalog. Session, rate, sequence, clock, release and cost
gates remain. No local Combat or fitting-catalog load is added to the remote window.
