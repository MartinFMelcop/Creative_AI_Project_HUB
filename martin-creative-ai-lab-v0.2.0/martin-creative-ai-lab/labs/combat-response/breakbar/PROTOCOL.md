# Selected breakbar control: prospective verification protocol

## Question and scope

Can an original bounded Treatment Line consumer apply a source-backed protection/exposure cycle through its existing authoritative round owner, without confusing breaking protection with an applied control, suppressing DOT, granting damage, or refilling spent resources?

This protocol precedes the new browser execution; native implementation checks had already started in parallel, before this protocol was written. It is not a preregistration of implementation or native results. The experimental unit is one deterministic software trial. Actions, assertions, screenshots and repeated runs are overlapping observations, not independent samples, people or statistical evidence of balance.

## Source and destination boundary

OBSERVED_SOURCE: Rave `REGRAS_DE_COMBATE.csv` BBR-001 through BBR-005 distinguish protected control consumption, break, exposed application, restoration, light weight 1, hard weight 3 and no default DOT drain. BBR-010 supplies an explicit five-point mini-boss bar. BBR-006 retains boss-specific exceptions; no complete boss catalogue or universal immunity implementation is claimed. Source table status does not make the mechanic approved North Star canon.

The original consumer policy explicitly maps an applied control to suppression of that action's direct contact and pressure extension. It does not suppress end-round DOT. Light control is free; hard control spends one existing shared charge. Both consume an actual round and do zero target HP damage. These costs, timing, threat suppression and shared-charge policy are destination decisions, not recovered source timing or balanced recommendations.

## Frozen comparison and acceptance

Existing toxic practice is the baseline: HP100, target96, charges2, initial Poison3/Bleed3, direct contact20 and existing pressure/round/DOT owner. The new control practice begins with those same facts and bar5 protected. No candidate is tuned after outcomes.

1. Actual preparation does not create an encounter; explicit Begin does.
2. Protected light drains one and hard drains three. An action that reaches zero breaks protection but does not apply control to that same action. Its direct contact and DOT remain payable.
3. A control begun exposed applies, suppressing that action's direct contact and pressure, while existing DOT still resolves. It refills one or three. The application that fills five still applies; protection returns after it.
4. Light leaves charges unchanged; accepted hard spends exactly one. Insufficient-charge hard refuses atomically. No control damages target HP or supplies victory.
5. DOT, reads, redraw and wall time cannot drain/refill the bar. Ordinary commands cannot claim an applied control. Terminal contexts refuse further combat mutation.
6. Actual UI controls delegate host commands. Visible bar amount, protected/exposed state and last application follow authoritative state, including boundary actions. The browser oracle is separate from the native test suite.
7. A deliberately false bar/protection renderer must be detected by the same fidelity assertion after valid owner execution. A crash, startup error, missing selector or unsuccessful gameplay is not a successful negative control.
8. Source identities must remain stable during execution; preserve any actual failure and superseded producer. A later edit requires a new labelled run.

No sample size or score endpoint is predeclared: correctness gates are exact state transitions. A losing policy is retained rather than repaired through rule changes. No human audibility, reaction time, player preference, accessibility, physical device, Windows, Unity Player, Steam, full effects/passives, source Ruby/RMXP execution or commercial clearance is inferred.
